# Deployment recommendation

All variants use the same held-out 59 windows: 24 Normal, 18 Warning and 17 Critical. Each achieved 100% accuracy with a diagonal confusion matrix of 24, 18 and 17. Critical recall is 17/17, or 100%, exceeding the specified 95% point threshold. This small synthetic evaluation cannot establish performance across routes, sensors, seasons or real failure mechanisms. Independent field data and substantially more Critical examples are required before safety claims.

M2 uses 223 distinct training-only calibration rows, exceeding the required 200. Its full INT8 file is 3,552 bytes, 34.42% below M1's 5,416. M3 removes 11 of 32 first-layer units and six of 16 second-layer units. Seventeen of 48 units is 35.42%, the whole-unit approximation to the requested 35%. Physical compaction produces a 6-21-10-3 network with 400 parameters. Its INT8 file is 3,216 bytes, 40.62% below M1. Masked-versus-compacted probabilities differed by at most approximately 1.14e-12 before subsequent training.

Both integer models clip 35 validation feature values, affecting 35 rows, while retaining correct class predictions. These saturations are explicitly recorded rather than corrected using validation-derived calibration. The unbounded drift creates values beyond the training calibration range. Future development should use realistic operating envelopes, independent calibration coverage and operationally consistent labels. The prescribed D1 temperature-drift class remains Warning even when its physical temperature exceeds Critical limits; our separate temperature guard makes that mismatch visible.

Benchmarking ran on the team's Intel i5-13420H laptop through Docker/WSL2 using TensorFlow 2.14.1 TFLite built-in CPU kernels, one interpreter thread and no default delegates. Ten warm-up calls preceded 200 measured invocations per variant. Rotation of variant order reduced systematic ordering effects. The five-metric table reports invoke-only latency, not filtering, message transport or storage. We independently recomputed mean and p95 from the saved 600 timing samples. All model hashes and recorded confusion matrices matched.

The energy value is a proxy: process CPU utilisation divided across 12 logical processors scales the 45 W processor-base-power estimate, then multiplies by mean invocation time [5]. A separate five-second CPU probe supplies utilisation. Hybrid cores, simultaneous multithreading, frequency scaling, idle consumption and virtualisation limit this approximation. It is neither measured battery energy nor evidence that the truck node consumes 45 W.

M1 and M3 form the feasible latency-size Pareto frontier. M3 dominates M2 because it is smaller and faster with equal measured accuracy. We select M1 for the verified CPU demonstration because it has the lowest mean, p95 and energy proxy. Reserving approximately 40 seconds for initial collection leaves about 50,000 ms of a 90-second illustrative budget for processing and local alerting. M1's measured p95 is 0.001684 ms. Its 5.416 KB file is small relative to the proposed Pi's 8 GB RAM and microSD storage, but activation/runtime memory and sustained target latency still need profiling. An ARM64-compatible build and target measurements must precede the 85-truck hardware deployment. Model-file bytes alone do not describe peak working memory. Python, TensorFlow, activation tensors and queues also consume RAM. Accelerator TOPS cannot substitute for a supported graph, compatible operators and an actual target benchmark.

The provisional Pi CPU pilot candidate is M1, gated on an ARM64-compatible runtime, actual target memory/latency/power measurements and a larger operationally consistent field evaluation before all 85 trucks receive it. M3 is the storage-efficient measured alternative. No Hailo delegation, target power compliance or pharmaceutical field-safety guarantee is established by the laptop benchmark.
